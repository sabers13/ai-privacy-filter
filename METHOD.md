# Evaluation method

**Protocol version 1.0, written 2026-10-27, before any test-split number was
produced.** This file fixes the evaluation before the first final number is
seen. It governs every number this project publishes about detection, leakage,
over-masking, restoration and triage, including the page's `results.json` and
`examples.json`.

Evaluation answers four questions, in plain language:

1. **How much personal data does the filter catch?** Per-type recall on
   synthetic enquiries and on GermEval 2014, with 95 % intervals.
2. **How often does any personal data still reach the AI?** Leak rate: the share
   of synthetic test enquiries whose outbound prompt contains at least one gold
   value, with a 95 % interval.
3. **How much non-personal text is replaced?** Over-masking: extra characters
   and affected enquiries.
4. **How well do the backends sort and draft on placeholders only?** Joint
   category + urgency accuracy on a fixed 40-enquiry subset, median latency,
   failures and a small draft-quality rubric.

There are **no pass thresholds**. Every number is reported as measured,
including misses, failures and any case where a simpler baseline wins. A
negative result is a result, not a reason to change the method.

The dataset is synthetic or public. No real customer data, no real person's
data and no private infrastructure detail appears in any input, log, artifact
or screenshot. GermEval text never leaves `data/external/` and is never sent to
an LLM.

---

## 1. Scope and order of work

This protocol applies to:

| task | what it produces |
|---|---|
| T11 | evaluation harness, detection numbers, leakage and over-masking, restore round-trip |
| T12 | live backend triage numbers on the fixed 40-enquiry subset |
| T13 | end-to-end numbers, if any are published |
| T14 | page data (`results.json`, `examples.json`) and page wording |

The work order is fixed: T10 lands this file; only then may T11 or T12 read a
test split. Tuning may happen before that on dev/train only.

The production pipeline under test is:

```text
detect -> pseudonymise (redact) -> guard -> prompt -> backend -> restore
```

Detection is local. The backend call is the only step that may use the network.
The filter path itself is covered by the socket-disabled test
(`make test-local`); that test, not this document, is the evidence for "runs
entirely on your machine".

The filter **pseudonymises** text by replacing values with placeholders. It does
not make text anonymous, and nothing here is legal advice.

### 2.2 GermEval 2014

| train | 24,000 | 29,078 | 12,934 | tuning only |
| dev | 2,200 | 2,674 | 1,207 | tuning only |

| file | SHA-256 |

The loader validates size and checksum. A mismatch stops the run; it is never
silently accepted.

Class mapping:

| GermEval outer tag | loader class | counted as personal data? |
|---|---|---|
| PER | PERSON | yes, primary |
| ORG | ORG | yes |
| LOC | LOCATION | **no**, reported separately |
| OTH | OTHER | no, not scored |
| `*deriv`, `*part` | own class | no, excluded |

**LOCATION is not a detection target of this filter.** `EntityType` has no
LOCATION member and the detector never emits one. Its class recall is therefore
0 % by construction; reporting that as a failure would be misleading. Instead
the report states the LOC gold count and, separately, the **incidental
coverage**: the share of LOC gold spans fully covered by any predicted
personal-data span. That number is informational only and is never folded into
the personal-data recall.

No GermEval sentence is committed, shown on the page, logged with its text, or
sent to an LLM or any other network service.

### 2.3 Split discipline

- **Tune only** on synthetic dev (80) and GermEval train/dev.
- **Final numbers only** on synthetic test (160) and GermEval test (5,100).
- Test data is read once per evaluation stage. Any later read of the same stage
  is a rerun and must be listed (§5).
- No test record, label or metric is used to choose a threshold, a pattern, a
  prompt, a backend setting or a subset.
- The fixed triage subset (§8) is part of the test split and may not be
  replaced, reordered or filtered after it is first used.

## 3. Systems under test

Three detection configurations are evaluated on the same inputs. All three are
reported for every detection table. If a simpler baseline wins any type, the
report says so in that table's caption and in the plain-language summary.

### 3.1 B0 — regex-only (the browser try-it box)

B0 is a fixed pattern rule set with **no statistical model, no name list and no
PERSON/ORG detection**. It is the rule set the page's try-it box runs in the
browser. There is one source of truth for the patterns: `eval/baselines.py`
(created by T11) exports the rules and `web/tryit-rules.json` is generated from
them; the browser box loads that JSON. A parity test over the 50 fixture texts
in `tests/fixtures/synthetic_texts.json` and all 160 synthetic test texts must
produce identical spans from the Python rules and the box. If parity cannot be
achieved, B0 is still scored from the Python rules, and the report states that
the box differs instead of calling them the same.

Required rule behaviour:

| type | rule (behaviour, not a particular regex spelling) |
|---|---|
| EMAIL | local part, `@`, domain, dot, 2+ letter TLD |
| URL | `http://`, `https://` or `www.` followed by non-space; trailing `.,;:!?)]}` trimmed |
| IBAN | `DE` + 2 check digits + 4 groups, optional single spaces; mod-97 must pass |
| PHONE | German form with optional `+49`/`0049`/leading `0`, separators space, `-`, `/`, `()`; at least 6 significant digits; no dots between groups |
| VAT_ID | `DE` + exactly 9 digits |
| POSTCODE_CITY | 5-digit German postcode, space, one or more capitalised city words |
| ADDRESS_STREET | capitalised street name ending in a common German street suffix, space, house number with optional letter |
| DATE_OF_BIRTH | numeric date `D.M.YYYY` only when a birth cue (`geboren`, `Geburtsdatum`, `Geburtstag`, `geb.`) occurs within 40 characters |

B0 has no PERSON/ORG rule, so its PERSON and ORG recall is **0 % by
construction**. It is included to show what a simple page-level filter achieves,
not as a straw man and not as the product.

Overlap resolution for B0: longest match first, then the type priority in §6.4,
then leftmost. A losing overlapping match is discarded. Every B0 span has score
`1.0` and source `b0:<rule>`.

### 3.2 B1 — Presidio defaults with the German spaCy model

B1 is Presidio exactly as shipped, with the pinned German pipeline and **no
custom recognizers and no tuning**:

- `AnalyzerEngine` with Presidio's default recognizer registry;
- `NlpEngineProvider` configured for `de_core_news_lg` (the same pinned wheel as
  the product), `supported_languages=["de"]`;
- `default_score_threshold=0.0`, `language="de"`;
- requested entities restricted to the ten `EntityType` names mapped at the
  edge; `LOCATION` and other unmapped Presidio types are dropped;
- no `merge_spans` call, no German cleanup, no context boosting, no first-name
  gazetteer, no German pattern recognizers.

Presidio's default email validation may consult the public-suffix list. The
cache is prepared once before the run and its hash is recorded; no per-enquiry
network call is allowed. B1 is deliberately the untuned baseline; if it beats
B2 on a type, that is a finding, not a bug to tune away.

### 3.3 B2 — full configuration (product detector)

B2 is `detect.detect(text, profile=<frozen profile>)` from
`src/ai_privacy_filter/detect.py`: spaCy German NER, Presidio email/URL, all
German recognizers, the shared merge rule and the NER cleanup.

The profile is **chosen on dev only** by the rule in §4 and frozen before the
test run. The frozen choice is recorded in `eval/configs.json` with a config
hash; the test run pins that hash. A code change to any detection file after
the choice is a configuration change and is handled as a rerun (§5).

B2 is the only configuration that may be tuned. B0 and B1 are fixed and are
never tuned on any split.

## 4. Tuning on dev only

### 4.1 What may be tuned

Only the detector configuration may be tuned:

- the `Profile` value (`balanced` or `strict`);
- any additional detector knob that exists in the source at the start of
  tuning and is declared in `eval/candidates.json` before the first tuning run.

Patterns, thresholds, profile definitions and candidate variants are all frozen
before test. The triage prompt and backend call settings may be compared on
synthetic dev, but the chosen prompt/settings are frozen before the test run in
the same way.

The triage subset (§8), metric definitions, matching rules, baselines, guard,
pseudonymisation, restore and statistical method are **not tunable**.

### 4.2 Selection rule (pre-registered)

For each candidate, compute the §6 recall on:

- synthetic dev: PERSON, ORG, EMAIL, PHONE, IBAN, ADDRESS_STREET,
  POSTCODE_CITY (the seven types with dev gold);
- GermEval dev: PERSON and ORG.

That is nine recall values. Let `r_min` be the smallest of them.

Choose the candidate with the **highest `r_min`** (privacy-first: no type may be
sacrificed to raise the average). Ties are broken, in order, by:

1. lower enquiry-level over-masking rate on synthetic dev (§7.4);
2. higher macro-average precision over the same nine type/split pairs;
3. `balanced` before `strict` (fixed alphabetical tie-break).

All candidates and all nine dev values are recorded in `results/tuning/`, with
the METHOD.md hash. The winner is written to `eval/configs.json` and committed
before the test run. If no candidate is clearly better, the simpler one wins by
the tie-break; the report says the difference was within noise rather than
inventing a winner.

Tuning runs are `mode=dev` and are not restricted by the test-run guard. They
still pin the data hashes and METHOD.md hash so the provenance is visible.

## 5. Test run, method hash and reruns

### 5.1 One run per stage

A **test run** is one invocation that reads a test split. There are two final
stages:

| stage | reads | produces |
|---|---|---|
| `detection` | synthetic test, GermEval test | recall, precision, leak rate, over-masking, restore round-trip |
| `triage` | the fixed 40-enquiry subset of synthetic test | accuracy, latency, failures, draft indicators |

A stage runs **once**. A second run of the same stage is a rerun and must carry
`--rerun-reason` and a row in `docs/eval-reruns.md`. Running the triage stage
after the detection stage is not a rerun (different stage), but only if
METHOD.md has not changed and the detection-relevant code has not changed. If
code that detection uses changed after the detection run, detection must be
rerun with a reason; the final report may not mix a stale detection number with
newer code.

Run identifiers are unique and immutable:
`<UTC-stamp>-<stage>-<short-commit>`, for example
`20261027T140000Z-detection-abc1234`.

### 5.2 METHOD.md hash guard

The guard is implemented now in `scripts/method_guard.py`; T11/T12 must call it
**before reading any test record**. It is not advisory; it writes a durable
test-access claim and refuses to continue without one.

```text
uv run python scripts/method_guard.py \
  --mode test --stage detection \
  --run-id 20261027T140000Z-detection-abc1234
```

For a rerun, add `--rerun-reason "<why>"`. If METHOD.md changed since **any**
earlier test access, add `--method-approval "<captain approval reference>"` as
well.

Rules enforced by the script:

1. `--mode dev` is always allowed and writes no claim.
2. `--mode test` requires `--run-id` and a clean tracked tree
   (`git status --porcelain --untracked-files=no` is empty), `METHOD.md` tracked
   and equal to `HEAD`, and a readable git commit. Untracked result files are
   allowed; uncommitted code or document edits are not.
3. The method hash is SHA-256 over the raw bytes of `METHOD.md`; the git blob
   hash is recorded too.
4. Prior test access is read from `results/runs/claims/*.json` and
   `results/runs/*/run.json`. A malformed or unreadable prior record fails
   closed (exit 5); it is never ignored.
5. First access for a stage: allowed.
6. New stage after another stage, with the same METHOD.md hash: allowed without
   a reason.
7. Repeat of a stage with the same hash: refused unless `--rerun-reason` is a
   non-empty string (exit 3).
8. Any test access after a METHOD.md hash change: refused unless both
   `--rerun-reason` and `--method-approval` are given (exit 3 for the missing
   reason, exit 4 for the missing approval). A byte change of any kind counts —
   there is no "typo" exemption.
9. Same `--run-id` called twice is idempotent only when stage, mode and hash
   match; anything else is a run-id conflict (exit 6).
10. If the claim cannot be written, the run does not start (exit 2). A crash
    after the claim still leaves the access on record, so the next attempt
    needs a reason.

Exit codes: `0` allowed, `2` usage/IO, `3` missing rerun reason, `4` missing
method approval, `5` malformed prior record, `6` run-id conflict, `7` dirty or
untracked METHOD.md tree. The script prints one JSON object on success and one
plain line on refusal; neither contains text from any enquiry.

The claim file (`results/runs/claims/<run-id>.json`) and the run record contain
only hashes, ids, stage, timestamps, reason and approval reference. They never
contain text or personal data.

Before reading test data, the harness writes
`results/runs/<run-id>/run.json` with `status: "running"` and flushes it. It
updates the record to `complete` or `aborted` at the end:

{

An `aborted` test run is still a test access and is listed in the rerun table.

### 5.4 Rerun table

`docs/eval-reruns.md` is append-only. The harness appends a row **before**
reading test data; if it cannot write the file, the run aborts.

| column | meaning |
|---|---|
| `#` | row number |
| `finished_at` | UTC timestamp |
| `run_id` | the run identifier |
| `stage` | detection or triage |
| `commit` | code commit |
| `method` | first 12 hex of the METHOD.md hash |
| `changed_since` | what changed since the previous run of this stage (code, config, data, method, first run) |
| `reason` | the `--rerun-reason` text, or `first run` |
| `test_seen_before_change` | `yes` when test numbers existed before the change, else `no` |
| `approval` | captain approval reference when the method changed, else `-` |

If a rerun is due to a code change, the report links the row and repeats the
reason next to the affected table. Reruns are never hidden and never described
as the first run.

### 5.5 Method changes after test numbers exist

After any test number has been seen, **do not edit METHOD.md**. Stop, append
`needs-decision` to the task status, and wait for the captain. If the captain
approves a change on return:

1. record the approval reference;
2. edit and commit METHOD.md;
3. rerun every affected stage with `--rerun-reason` and `--method-approval`;
4. add the rerun rows;
5. report both the old and new numbers, clearly labelled.

A request to change the method after final numbers exist is escalated even if
it looks cosmetic. The hash guard enforces the mechanical part; the escalation
rule covers the human part.

## 6. Matching rules

These rules are fixed for synthetic and GermEval data. They are applied by one
scoring function; there is no per-dataset hand adjustment.

### 6.1 Units and offsets

- Gold and predicted spans are half-open `[start, end)` character ranges.
- Offsets index the exact input string. No Unicode normalisation, trimming or
  whitespace rewriting occurs before matching. A detector that changes offsets
  by normalising text would score as a miss.
- Synthetic gold spans are character-exact: `text[start:end] == span.text`.
- GermEval gold spans are the outer spans of the joined token text.
- A gold span occurrence is one evaluation unit, even if the same value appears
  several times. Repeated values count separately.

### 6.2 Predicted spans

- Predictions are exactly what the configuration returns; no post-hoc
  filtering, score cut, type rewriting or manual repair.
- Exact duplicate predictions with the same `(start, end, type)` are collapsed
  once; the first by score, then source, is kept. This only removes identical
  duplicates, not overlaps.
- Zero-length, whitespace-only and out-of-range predictions are ignored (the
  detector should not emit them; if it does, the run logs a warning count).
- Overlapping predictions of different types are all kept. Coverage uses their
  union; precision counts each prediction separately.

### 6.3 Compatible types

A predicted span protects a gold span when its type is compatible with the gold
type. Compatibility is exactly this table; every pair not listed is
incompatible.

| gold type | protecting predicted types | why |
|---|---|---|
| PERSON | PERSON, ORG | a name inside a company name is removed when the company is removed |
| ORG | ORG, PERSON | an organisation labelled as a person is still removed |
| EMAIL | EMAIL, URL | the address is removed either way |
| URL | URL, EMAIL | same |
| PHONE | PHONE | |
| IBAN | IBAN | |
| ADDRESS_STREET | ADDRESS_STREET | |
| POSTCODE_CITY | POSTCODE_CITY | |
| VAT_ID | VAT_ID | |
| DATE_OF_BIRTH | DATE_OF_BIRTH | |

Because the PERSON/ORG and EMAIL/URL relaxations could hide type confusion, the
report also prints **strict same-type recall** as a secondary column. The
primary per-type recall uses the table above; the strict column uses equality
only. Both are reported with counts and Wilson intervals.

### 6.4 Full coverage (primary privacy view)

A gold span is **protected** when every character position in it is inside at
least one predicted span of a compatible type. Coverage may come from several
adjacent predicted spans; a gold span split into two correct pieces counts as
protected.

A gold span is **partially covered** when at least one character is inside a
compatible prediction but the span is not fully protected.

A gold span is **missed** when no character is inside a compatible prediction.

For overlap resolution inside a single baseline's raw output, the fixed type
priority is:

```text
EMAIL, IBAN, URL, VAT_ID, PHONE, ADDRESS_STREET, POSTCODE_CITY,
DATE_OF_BIRTH, ORG, PERSON
```

### 6.5 Precision

A predicted span of type `T` is **correct** when its entire range is inside a
gold span whose type is compatible with `T` (the same table, read in the other
direction). A prediction that covers a gold span plus extra characters is
**not** correct: the extra text is over-masking, and precision must show it. A
prediction split into two pieces inside one gold span counts twice as correct;
that is the price of counting span occurrences, and it is stated in the report.

Exact-boundary precision (start and end equal to a gold span) is reported as a
secondary column, because containment precision can look generous.

## 7. Metrics

All percentages are accompanied by the raw numerator and denominator. No
percentage is reported without its counts. Intervals are 95 % Wilson score
intervals unless a metric says otherwise.

### 7.1 Recall per type

```text
recall(type) = protected gold spans of that type / all gold spans of that type
```

Reported per type for synthetic test and for GermEval test (PERSON, ORG,
LOCATION separately as described in §2.2), for B0, B1 and B2.

Each row shows: type, gold spans `n`, protected count, recall, Wilson interval,
strict same-type protected count, strict recall, partial count, missed count.
If `n = 0`, write `not estimable (no gold spans)` and do not print a percentage.

### 7.2 Precision per type

```text
precision(type) = correct predicted spans of that type / all predicted spans of that type
```

Reported with the same baselines and intervals, plus exact-boundary precision.
If there are no predictions of a type, write `n/a (0 predictions)`.

### 7.3 Leak rate

For each synthetic test enquiry:

1. run B2 detection on the original text;
2. redact and guard with the production functions;
3. build the exact prompt the backend would receive;
4. audit that **prompt string** against the gold values, not against the
   detector's mapping.

An enquiry counts as **leaked** when any gold value occurs in the outbound
prompt after:

- NFC normalisation, case folding and whitespace collapsing;
- for PHONE and IBAN, also comparison of ASCII digits only, at least four
  digits, so reformatting does not hide a leak.

The audit uses gold values, so a value the detector missed is caught here even
though the production guard only knows mapped values. That is the point: the
leak rate is an independent audit of what actually leaves the machine, not a
restatement of the guard.

```text
leak_rate = leaked enquiries / 160
```

Reported with a Wilson interval, the number of leaked enquiries, the leaked
types (types only, never values), and the number of gold spans missed. The same
metric is computed for B0 and B1 so the baselines are comparable.

Also reported separately:

- **guard blocks**: enquiries where the production guard refused the outbound
  text. The guard only sees mapped values, so a missed value is not a guard
  block; the difference between leaks and blocks is reported, not hidden.
- **residual gold characters**: gold characters not inside any compatible
  prediction, divided by all gold characters, with a cluster bootstrap interval
  by enquiry. This is the character-level counterpart to span recall.

No prompt that leaks is written to disk. The artifact stores the run id, the
enquiry id, the leaked types and the boolean only.

### 7.4 Over-masking

For synthetic test, over-masking uses the union of all gold spans (any type) as
the protected set.

- **Extra characters**: characters inside a predicted span but outside every
  gold span.
- **Enquiry-level over-masking rate**: share of the 160 enquiries with at least
  one extra character, Wilson interval.
- **Character-level over-masking rate**: extra characters divided by all
  replaced characters, with a 95 % cluster bootstrap interval by enquiry
  (§9.2). If nothing was replaced, write `n/a`.
- **Fully false spans**: predicted spans with no character inside any gold
  span, reported as a count and a share of predictions.
- **Extra characters by predicted type**: a small table showing which detector
  is responsible.

Over-masking is also reported for B0 and B1 with the same rules, so a baseline
that replaces half the text is visible as such.

For GermEval, the same character-level calculation is a secondary number using
the union of PER, ORG, LOC and OTH outer gold spans as the protected set. It is
labelled secondary because Wikipedia/news text is not an enquiry and because
the gold set covers classes the filter does not target.

### 7.5 Restore exactness

Two checks, both reported; the round-trip is the headline.

**Round-trip exactness (headline).** For each synthetic test enquiry:

```text
restore(redact(text, spans = B2 detection)).text == text   # byte-for-byte
```

Exactness = exact round-trips / 160, Wilson interval. Missed values stay in the
text on both sides, so this metric measures the fidelity of redaction and
restoration, **not** recall. A failure caused by a repeated value with different
casing or spacing is counted as a failure and listed by enquiry id and reason
(`normalisation variant`); no value is printed.

**Draft restoration (per backend).** On the fixed 40-enquiry subset, for each
successful backend draft:

- count mapped placeholder occurrences in the redacted draft;
- count how many are restored to their original in the restored draft;
- count unknown/invented placeholders;
- a draft is **restore-exact** when every mapped placeholder occurrence is
  restored and there are zero unknown placeholders.

Report: drafts scored, restore-exact count and share with Wilson interval,
unresolved mapped placeholder count, drafts with an unknown placeholder, and
drafts with no placeholders (reported separately because they are trivially
exact).

### 7.6 Triage accuracy

The fixed 40-enquiry subset (§8) is sent to every available backend once.

- **Primary**: joint exact match of `category` **and** `urgency`.
- **Secondary**: category-only accuracy and urgency-only accuracy.
- Denominator is **40 for every backend** (intention-to-treat). A backend error,
  timeout or guard block is not dropped; it counts as an incorrect answer for
  accuracy and is reported separately as a failure. This prevents a backend
  from improving its score by failing.
- Report joint, category-only and urgency-only accuracy with Wilson intervals,
  plus 5×5 and 3×3 confusion matrices.
- Report counts of success, backend error (by `error_kind`), guard block and
  schema-invalid reply.
- **Median latency** over successful calls only: `BackendResult.latency_ms`
  includes the network/CLI call and excludes prompt building, redaction and
  guard. Report `n`, median, minimum, maximum and nearest-rank p95. An even
  count uses the mean of the two middle values; report milliseconds to one
  decimal. Latency is a single-machine observation, not a benchmark.
- The same 40 records are used for every backend, in the listed order. No
  retries, no fallback to another backend on failure, no reordering between
  backends.
- One warm-up call per backend on synthetic **dev** record `syn-dev-0001` (or
  the first dev record if that id is absent) is allowed to load a model; it is
  not scored, not counted in the 40, and is recorded in the run metadata. If
  the warm-up fails, the backend is still attempted on the 40.

The `fake` backend may be run over the 40 as a harness smoke test. It is
deterministic pseudo-random output and is **not** reported as an AI backend or
included in quality claims; it only proves the pipeline wiring.

### 7.7 Draft quality on placeholders

Quality is judged only on prompts that contain placeholders and no gold values.
Any prompt that failed the §7.3 audit is excluded from quality scoring and
reported as a leak instead.

**Automated indicators**, per backend over the 40:

- schema-valid reply rate;
- non-empty draft rate;
- drafts containing at least one input placeholder;
- drafts containing an unknown/invented placeholder;
- drafts containing any gold value (must be 0; if not, it is a leak and a guard
  failure, reported as such);
- median draft length in characters.

**Manual rubric**, per backend on a fixed 10 of the 40 (positions 1, 5, 9, ...,
37 in the §8 order):

| dimension | 0 | 1 | 2 |
|---|---|---|---|
| relevance | does not address the request | partly addresses it | directly addresses it |
| placeholder handling | invents placeholders or misuses them | uses some correctly | uses only input placeholders correctly |
| German quality | hard to read or wrong register | understandable with errors | clean, appropriate register |

Scoring procedure: backend and model labels are removed, drafts are shuffled
with seed `20261027`, one reviewer scores all drafts, and the scores are joined
back by run id afterwards. Report mean and range per dimension and per backend,
plus the number of drafts with an invented fact. There is no combined "quality
score" and no pass threshold; the three dimensions stay separate because they
can move in opposite directions. A single reviewer is a limitation, stated in
the report.

### 7.8 GermEval specifics

- Evaluate each of the 5,100 test sentences independently; no cross-sentence
  context.
- Primary: **PERSON recall**. Also **ORG recall**. Report precision per type
  and the micro (PERSON + ORG) recall as a summary, all with Wilson intervals.
- LOCATION: gold count and incidental coverage only, as in §2.2. Never include
  it in the personal-data recall, never call it personal data on its own.
- B0's 0 % PERSON/ORG recall is shown, not hidden.
- Exact-boundary precision is reported alongside containment precision.
- No GermEval text is sent to a backend. Detection only.

## 8. Fixed triage subset (40 enquiries)

### 8.1 Selection rule

Test records are grouped by `gold_category` in this fixed order:

```text
QUOTE_REQUEST, SUPPORT, JOB_APPLICATION, PARTNERSHIP, OTHER
```

Within each category, records are sorted by id ascending. The selected
**1-based positions** are:

```text
1, 5, 9, 13, 17, 21, 25, 29
```

That is 8 per category and 40 in total. The rule is reproducible from the
committed corpus and is checked by `tests/test_method.py`. It was fixed before
any detection or triage number was produced. The step of four spreads the seven
styles across each category; the resulting subset contains every style at least
five times.

Category and urgency distribution: 8 per category; 24 NORMAL, 8 HIGH, 8 LOW.
Urgency is tied to category in this corpus (JOB_APPLICATION is HIGH,
OTHER is LOW, the rest NORMAL), so urgency-only accuracy is **not** independent
evidence of urgency skill. The report says this next to the table.

## 9. Statistics

### 9.1 Wilson 95 % interval

For `k` successes in `n` trials and `p = k / n`, with
`z = 1.959963984540054`:

```text
centre = (p + z²/(2n)) / (1 + z²/n)
half   = z * sqrt(p(1-p)/n + z²/(4n²)) / (1 + z²/n)
lower  = max(0, centre - half)
upper  = min(1, centre + half)
```

This is the score interval, not the normal approximation. It is used for every
proportion: recall, precision, leak rate, over-masking enquiry rate and triage
accuracy. It is well behaved at 0 and 1, so a zero-leak result still gets a
finite upper bound.

### 9.2 Clustered sensitivity check

Spans inside one enquiry are not independent, and sentences inside one GermEval
document are not independent. Wilson intervals are required and remain the
reported interval; a cluster bootstrap is added as a sensitivity check for the
two character-level metrics and as an optional second column for recall.

- Resample whole enquiries (synthetic) or sentences (GermEval) with replacement,
  10,000 times;
- seed `20261027`;
- recompute the ratio in each resample;
- report the 2.5th and 97.5th percentiles with linear interpolation
  (`numpy.percentile(..., method="linear")`).

Where a resample has a zero denominator, skip that resample and report the
number skipped. If the Wilson and bootstrap intervals disagree materially, say
so; do not pick the narrower one.

### 9.3 Rounding and presentation

- Counts are integers and always shown.
- Percentages: one decimal place, computed from unrounded counts.
- Latency: one decimal place in milliseconds.
- Intervals: one decimal place.
- No p-values and no significance claims. The intervals are descriptive.
- No metric is dropped because it is unflattering or because a baseline wins.
  If a type has no predictions or no gold, say why rather than leaving a blank.

## 10. Backends and call configuration

Every available real backend is evaluated on the same 40 enquiries. Backends
are not part of the privacy filter's detection claims; they are measured
separately.

| backend | availability | call settings |
|---|---|---|
| `byok` | `AIPF_BYOK_BASE_URL` and `AIPF_BYOK_API_KEY` configured | one chat completion, `max_tokens=2000`, JSON category/urgency/draft, fresh `x-opencode-session` UUID per enquiry, timeout 120 s |
| `claude-cli` | `claude` binary and subscription login present | tools-off invocation per `docs/backends.md`, timeout 120 s |
| `codex-cli` | `codex` binary and login present | tools-off invocation per `docs/backends.md`, timeout 120 s |
| `ollama` | local tunnel and model present | `BYOKBackend.for_ollama()`, `max_tokens=300`, JSON-schema response, timeout 90 s |
| `fake` | always | harness smoke test only; not a quality result |

Rules:

- Availability is probed **before** the 40 and recorded. An unavailable backend
  is reported as unavailable with the reason (`not configured`, `no login`,
  `tunnel down`, `model missing`); it is not silently dropped and not replaced.
- No retries and no fallback to another backend. A failure is a result.
- The same prompt template, category set and urgency set are used for every
  backend. The prompt asks for strict JSON against `TRIAGE_SCHEMA`.
- The outbound prompt is audited against gold values before the call (§7.3). No
  call is made when the production guard blocks.
- A fresh session id per enquiry; no provider-side session reuse.
- Model ids that come from private configuration are recorded as a short hash,
  never printed. Provider-reported model ids returned by a CLI may be recorded
  if they are public; when in doubt, hash.
- The live-LLM lock (`state/aipf-lock-live-llm`) is held for the live run so at
  most one caller is active. It is released when the run ends, including on
  failure. The Ollama stage also respects the server lock if an install/pull is
  in progress. Locks are never held while idle.
- No server hostname, IP, username, key or absolute home path enters the
  repository, the artifacts, the logs or a screenshot. Connection details come
  from the private environment at runtime.

If every real backend is unavailable, the triage section reports
`not measured (no backend available)` and the detection results stand on their
own. That is not a reason to substitute a simulated backend for a real one.

## 11. Artifacts and reproduction

Each test stage writes under `results/runs/<run-id>/`:

| file | contents |
|---|---|
| `run.json` | §5.3 record |
| `metrics.json` | every metric, count, interval, per type and per baseline/backend |
| `report.md` | the human-readable report described in §12 |
| `responses/<backend>/<enquiry>.json` | parsed reply, latency, usage, error kind; **never** a reply containing a gold value |
| `scoring/` | per-enquiry booleans and type lists, no text |

`make reproduce` rebuilds `metrics.json` and `report.md` from stored responses
and the committed corpus, with no network and no LLM call. It must reproduce
every number except timestamps; if it cannot, the difference is a bug and is
reported. Deterministic detection depends on the pinned model and package
versions recorded in `run.json`.

If a reply contains a gold value, it is not stored. The response record keeps
the error kind `leak`, the backend, the model hash, the latency and the leaked
types; the text is discarded.

The final page data is written from the latest accepted run:

- `results.json`: `detection.synthetic`, `detection.germeval` and
  `triage.per_backend` each carry `run_id`, `method_sha256`, `commit`, counts,
  intervals and the baseline/backend name. `meta.mock` is `false`.
- `examples.json`: synthetic enquiries only, `mock: false`, with `spans` and
  `misses` from the displayed detector. No GermEval sentence and no real data.

The page always says "not legal advice" and uses "pseudonymises"; it makes no
anonymity claim and no legal-compliance claim.

## 12. Reporting

Every report starts with the four plain-language answers, each with a number
and its interval:

1. **Caught:** for the main types, `protected / total` and the percentage, with
   the worst type named explicitly.
2. **Leaked:** `leaked / 160` enquiries, the percentage and the upper bound,
   plus the missed-span count and whether the guard caught the leak.
3. **Over-masked:** the enquiry share and the character share, with the worst
   type named.
4. **Backend quality:** joint accuracy `correct / 40`, median latency, failure
   count, and the draft rubric means.

Then the detail tables:

- synthetic test: per-type recall/precision for B0, B1 and B2, with intervals,
  strict recall and exact precision;
- GermEval test: PERSON (primary), ORG, LOCATION incidental, per baseline;
- leak rate for B0, B1 and B2, with leaked types and residual characters;
- over-masking for B0, B1 and B2;
- restore round-trip and per-backend draft restoration;
- triage per backend: joint/category/urgency accuracy, confusion matrices,
  latency, failures;
- draft indicators and rubric scores.

Every table caption says which baseline wins and by how much. If B0 or B1 wins
a type, the caption says "simpler baseline B1 wins PERSON recall by X points"
in plain words. No table is omitted because it is disappointing.

The report closes with limitations:

- synthetic enquiries are template-generated German, not real customer mail;
- 160 test enquiries and 40 triage enquiries are small;
- GermEval is Wikipedia/news, not enquiries, and has no EMAIL/PHONE/IBAN labels;
- Wilson intervals treat spans as trials and may be optimistic; the cluster
  bootstrap is the sensitivity check;
- urgency is confounded with category in the synthetic corpus;
- one sample per backend per enquiry; LLM output is not deterministic;
- latency is one machine and one network path, not a benchmark;
- one reviewer scores the draft rubric;
- no pass thresholds; these are descriptive measurements of pseudonymisation,
  not a compliance or legal claim.

## 13. Failure and escalation

- **No pass thresholds.** A low number is reported, not "failed". A run that
  completes is valid even when the filter misses entities or a backend is bad.
- **Data integrity failure** (synthetic hash mismatch, GermEval size/checksum
  mismatch, missing gold spans): stop, report `blocked`, do not score.
- **Malformed prior run record** in the hash guard: fail closed, report
  `blocked`; do not delete the record to get past it.
- **METHOD.md change after test numbers exist**: `needs-decision`, stop, wait
  for the captain (§5.5).
- **Missing environment variable, expired login, rejected key, unreachable
  server, sudo requirement, licence problem, quota wait over 12 h**: escalate
  per the standing list, do not improvise.
- **A backend failure**: record it and continue with the remaining backends.
  Do not retry silently and do not swap in a different model.
- **Any request to publish, push, open a PR or deploy**: not part of this
  protocol; escalate.

Nothing in this document overrides the project's no-real-data, no-private-
infrastructure and no-network-except-the-LLM rules.
